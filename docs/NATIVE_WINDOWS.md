## 2. Как собрать то, что есть

Нужны только Windows и Visual Studio (см. [раздел 11](#11-что-понадобится-для-сборки-и-для-пользователя)) и исходники
dynarmic и Boost.

```bat
host\build.cmd                     rem из Windows
```
```bash
host/build.sh                      # из WSL (запускает build.cmd на стороне Windows)
EW2_CMAKE_ARGS="-DDYNARMIC_DIR=D:/src/dynarmic -DBOOST_DIR=D:/src/boost" host/build.sh   # свои пути
host/build-native/ew2host.exe --selftest
```

Результат: `host/build-native/ew2host.exe` (7 МБ), первая сборка ~2 минуты (dynarmic ~165 файлов).
По умолчанию исходники ищутся в `third_party/dynarmic` и `third_party/boost` проекта, затем в соседнем проекте
`../eternity-warriors-3-probe/third_party/`. Откуда их брать:

- dynarmic: https://github.com/merryhime/dynarmic, собиралось на коммите `a46601580d5512d324104f985b5f0209dc980ddc`
  (подмодули — `git clone --recursive`);
- Boost (только заголовки, нужна папка, внутри которой `boost/`): https://www.boost.org/

## 3. Почему это не просто «скомпилировать под Windows»

Порт (`port/build/ew2`) — это **ARM32-программа для Linux**: он линкуется с glibc, создаёт потоки через `clone`, ловит
сигналы и пользуется ядром Linux для файлов и сокетов. Игра внутри него — тоже ARM-код (Android-библиотеки Unity и
Mono). Под Linux/WSL всё это исполняет `qemu-arm`, который эмулирует и процессор, и интерфейс ядра Linux. Под Windows
готового аналога нет (`qemu-user` существует только на Linux-хосте), поэтому нужно либо запускать целую виртуальную
машину с Linux, либо написать своего «эмулятора процесса Linux» поверх JIT. Второй путь — то, что начато в `host/`.

## 4. Какие пути возможны

| Путь | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Нативный хост на dynarmic** (выбран) | `ew2host.exe`: JIT ARM + свой слой системных вызовов Linux | один небольшой exe, без ядра и ВМ; быстрый старт; точная связь с хостовым GL/звуком | это работа на недели: загрузчик, потоки, сигналы, файлы |
| B. Виртуальная машина | `qemu-system-arm.exe` (xPack QEMU) + ядро Linux ARM + initrd с портом | почти всё уже есть в старом `play_win.py`, `third_party/qemu-guest/` | нужно собрать ядро с virtio, скачать QEMU; полная системная эмуляция тяжелее и медленнее; патчи скорости из `qemu/` для неё не действуют |
| C. Переписать порт под хост x86-64 | сам порт (загрузчик, JNI, thunks) собрать как Windows-программу, а ARM исполнять только для библиотек игры | самый быстрый итог | переработка всего порта: каждый вызов между игрой и портом должен идти через JIT |

Путь A выбран как самый перспективный; он же совпадает с планом, оставшимся в проекте EW3.

## 5. Архитектура нативного хоста

```
ew2host.exe  (один процесс Windows)
  ├─ main.c        разбор параметров, запуск потока гостя, остановка
  ├─ elf.c         загрузка ARM ELF в адресное пространство гостя, стек, auxv           [нет]
  ├─ mem.c         резерв 4 ГиБ, страницы, права, mmap/mprotect                          [есть]
  ├─ cpu.cpp       dynarmic: по ядру на поток гостя, svc → хост, ошибки доступа           [есть]
  ├─ thread.c      clone → поток Windows + ядро dynarmic, futex, tid, завершение          [нет]
  ├─ signal.c      rt_sigaction/tkill/sigaltstack, доставка сигналов, sigreturn           [нет]
  ├─ syscall.c     таблица системных вызовов Linux ARM EABI                              [нет]
  ├─ vfs.c         пути гостя → пути Windows, дескрипторы файлов и сокетов                [нет]
  └─ bridge        HTTP-заглушка серверов Glu, звук, ввод, связь с ew2gl.exe              [нет; сейчас Python и WSL]

ew2gl.exe  ◄── TCP 127.0.0.1:18090 (Winsock) ──  гость (GL-поток)       [есть, без изменений]
audio_sink ◄── канал ──                          гость (PCM FMOD)       [нужен вариант под Windows]
```

Гостевой адрес `A` лежит по адресу `g_mem + A`; таблица страниц dynarmic указывает на `g_mem` для отображённых страниц,
поэтому JIT читает и пишет память гостя напрямую, без вызовов хоста; обращение к неотображённой странице возвращается в
хост как ошибка (это основа для `SIGSEGV`).

## 6. Что нужно написать, по модулям

Оценка строк кода C — порядок величины.

### `elf.c` (~400 строк)
- разбор ELF32 ARM (`PT_LOAD`, `PT_INTERP`, `PT_TLS` при статической сборке), отображение сегментов в `g_mem` с нужными
  правами;
- начальный стек: `argc/argv/envp/auxv` (`AT_PHDR`, `AT_ENTRY`, `AT_PAGESZ`, `AT_RANDOM`, `AT_HWCAP` с флагами
  `vfp neon vfpv3 vfpv4 idiva idivt`, `AT_PLATFORM`);
- динамическая сборка: загрузить `ld-linux-armhf.so.3` как интерпретатор и держать rootfs с ~27 библиотеками
  (`/usr/lib/arm-linux-gnueabihf`), **либо** собрать порт статически (рекомендуется, см. [раздел 8](#8-изменения-в-самом-порте)).

### `syscall.c` (~1200 строк)
- диспетчер `host_svc` → номер в `r7`, аргументы `r0–r5`, результат в `r0`, ошибки как `-errno`;
- 52 вызова из [раздела 7](#7-системные-вызовы-которые-нужны-игре-по-strace); остальные возвращают `-ENOSYS` с записью в
  журнал, чтобы быстро находить недостающие;
- приватные вызовы ARM: `set_tls` (`0xF0005`), `cacheflush` (`0xF0002`, сбрасывает кэш трансляций dynarmic — нужно для
  JIT Mono и патчей кода в `libunity`).

### `vfs.c` (~600 строк)
- отображение путей: корень проекта, `ew2data/`, `Saves/`, `/tmp` → временная папка Windows, `/proc/self/exe`,
  `/sys/devices/system/cpu/present`, `/dev/null`, `/dev/urandom`; `/proc/cpuinfo` порт подменяет сам;
- преобразование `struct stat64` ARM EABI из `GetFileInformationByHandle`, `getdents64`, `_llseek`, `rename`, `mkdir`,
  `readlink` (в том числе по `…/main.431….obb/assets/...`, это `ENOTDIR`/`EINVAL` как под Linux);
- таблица гостевых дескрипторов: файлы (`HANDLE`) и сокеты (`SOCKET`) в одном пространстве чисел;
- UTF-8 ↔ UTF-16, длинные пути, регистр букв (файлы игры чувствительны к регистру).

### `thread.c` (~500 строк)
- `clone` с флагами `CLONE_VM|FS|FILES|SIGHAND|THREAD|SYSVSEM|SETTLS|PARENT_SETTID|CHILD_CLEARTID` (в запуске их 30):
  новый поток Windows со своим ядром dynarmic, `TPIDRURO` из `tls`, запись `tid` по `parent_tidptr`, при выходе
  обнуление `child_tidptr` и пробуждение ожидающих;
- `futex`: `FUTEX_PRIVATE_FLAG` + `WAIT`, `WAKE`, `WAIT_BITSET`, `CLOCK_REALTIME` (**51 тысяча вызовов за 45 секунд**,
  значит, нужен быстрый путь на `WaitOnAddress`/`WakeByAddress*` над памятью гостя);
- `set_tid_address`, `set_robust_list` (достаточно принять), `gettid`, `getpid`, `sched_yield`, `sched_getaffinity`
  (вернуть 4 или 8 процессоров), `sched_get*`, `exit`, `exit_group`.

### `signal.c` (~900 строк) — самая трудная часть
Эмуляция сигналов нужна, и не ради красоты:
- **Mono ловит `SIGSEGV`/`SIGBUS`/`SIGFPE`** для проверок указателей на `null` и исключений; доставка должна строить
  настоящий кадр сигнала ARM (`rt_sigframe`: `ucontext`, `sigcontext` с `r0–r15`, `cpsr`, `fault_address`) на стеке гостя
  или на `sigaltstack`, вызывать обработчик и по `sigreturn` восстанавливать регистры. В запуске 107 возвратов;
- **сборщик мусора Boehm останавливает потоки сигналами**: `tkill(tid, SIGPWR)` и `SIGXCPU`, обработчик ждёт в
  `rt_sigsuspend`, пока его не разбудят (122 вызова `tkill`, 52 `rt_sigsuspend`, 37 `sigaltstack`). Нужно прерывать
  ядро dynarmic в другом потоке (`cpu_halt`, уже есть), доставлять сигнал в точке, где поток остановился, и будить
  `sigsuspend`;
- `rt_sigaction` для SIGILL, SIGUSR2, SIGSEGV, SIGBUS, SIGFPE, SIGABRT(IOT), SIGPWR, SIGXCPU, SIGQUIT, SIGPIPE, 32, 33, 34;
  `rt_sigprocmask`;
- SIGILL порт использует для проверки доступности счётчика `CNTVCT`; в нативном хосте проще дать счётчик через CP15 или
  оставить `EW2_NO_CNTVCT=1`.

### Сокеты через Winsock (~300 строк)
Только `AF_INET`, `SOCK_STREAM`: `socket`, `connect`, `bind`, `listen`, `accept`, `send`, `recv`, `setsockopt`,
`fcntl64(F_GETFL)`. Нужны для HTTP-заглушки серверов (порт 18080) и GL-моста (гость слушает порт 18090, `ew2gl.exe`
подключается). Блокирующие вызовы должны прерываться сигналом.

### Мост и запуск (~500 строк)
- HTTP-заглушка серверов Glu (`tools/http_stub.py`) должна работать без Python: переписать на C внутри `ew2host`;
- звук: гость пишет PCM в fifo; на Windows это именованный канал или сокет и `audio_sink`/SDL2;
- ввод: `ew2gl.exe` пишет команды в файл `ctl/commands`, гость читает; работает как есть;
- упаковка: папка с `ew2host.exe`, `ew2gl.exe`, SDL2.dll, ANGLE (`libEGL.dll`, `libGLESv2.dll`), порт, данные игры.

## 8. Изменения в самом порте

1. **Статическая сборка `port/build/ew2`** (рекомендуется): без `ld.so` и без rootfs с 27 библиотеками. Нужен
   статический glibc armhf (в пакетах `libc6-dev:armhf` есть `libc.a`; `libzip.a`, `libbsd.a`, `libz.a` — в
   `-dev`-пакетах), а SDL-шим (`tools/sdl_shim.cpp`) подключить как обычный код. `dladdr` порт использует только в
   диагностике (`crash.cpp`, `pc_prof.cpp`); `dlopen`/`dlsym` для игры реализованы самим портом.
2. Переменные окружения и пути: `EW2_NO_CNTVCT=1`, `EW2_GL_LISTEN`, `EW2_SERVER`, `EW2_CONTROL_DIR`,
   `EW2_AUDIO_DEV` — те же, что в `play_wsl.sh`.
3. Fifo для звука (`/tmp/ew2_audio.fifo`) заменить на сокет или именованный канал.
4. Сборка с `-marm` и режимом ARM остаётся (Mono ловит Thumb по `cpuinfo`, порт его подменяет).

## 9. План работ и оценка

Один разработчик, знакомый с Linux ABI. Оценка грубая, без учёта отладки на реальной игре.

| Этап | Результат | Оценка |
|---|---|---|
| 0. Каркас (готово) | JIT и память на Windows, самопроверка | — |
| 1. `elf.c` + минимум системных вызовов | запуск **статических** ARM-программ (`armbench`, тесты NEON/VFP) и сверка с `qemu-arm` по хешам и времени | 3–5 дней |
| 2. Файловая система и время | `vfs.c`, `stat64`, чтение игровых данных, `clock_gettime64`, сокеты | 4–6 дней |
| 3. Потоки и `futex` | `clone`, TLS, `futex`, завершение потоков | 3–5 дней |
| 4. Сигналы | `SIGSEGV` для Mono, остановка потоков GC, `sigreturn` | 5–8 дней |
| 5. Интеграция с игрой | загрузка `ew2`, GL/звук/ввод/HTTP, окно, сохранения | 4–6 дней |
| 6. Отладка и скорость | прогон меню, города, боя; сверка с `qemu-arm`; профилирование; поддержка недостающих инструкций (`InterpreterFallback`) | 1–3 недели |
| 7. Упаковка | портативная папка, запуск двойным кликом, без Python | 2–3 дня |

Итого порядка **1–1,5 месяцев** работы одного человека. Самое рискованное — этапы 4 и 6.

Проверка по ходу работы: на каждом этапе гонять те же тестовые программы и тот же `strace`-журнал (`QEMU_STRACE=1`) как
эталон; сравнивать порядок и аргументы системных вызовов нативного хоста с `qemu-arm`.

## 10. Риски

- **Сигналы и остановка потоков сборщиком мусора** — самый тонкий момент: ошибка даёт редкие зависания и падения.
- **Покрытие инструкций dynarmic**: незнакомая инструкция заканчивается `InterpreterFallback` и падением; нужно прогнать
  все NEON-пути движка (скиннинг). Помогает то, что `qemu/` уже содержит тесты для сверки результатов.
- **Скорость**: 4 ГиБ резерв и таблица страниц фиксированы, но `futex`-нагрузка (51 тысяча вызовов) и 261 тысяча
  `clock_gettime64` должны идти без лишних переходов; код-кэш dynarmic (128 МБ) и инвалидация при записи JIT-кода Mono
  тоже влияют на кадр.
- **Антивирусы** иногда реагируют на программы с JIT и страницами `RWX`.
- **Динамическая сборка** (если не делать статическую) требует аккуратной эмуляции `ld.so`: `AT_*`, TLS, `dl_iterate_phdr`.
- **Android**: нативный хост — только для Windows; для Android остаётся путь с `qemu-arm` (`qemu/patches/`).

Для сборки `ew2host.exe` (разработчик):

|---|---|
| Windows 10/11 x64 | сборка и запуск |
| Visual Studio 2022 или новее (Community) с нагрузкой «Разработка настольных приложений на C++» | компилятор MSVC, CMake и Ninja входят в состав |
| исходники dynarmic (коммит из раздела 2) и заголовки Boost | зависимости JIT, сборка из исходников, глобально не ставятся |
| ARM-кросс-компилятор в WSL (`gcc-arm-linux-gnueabihf`) | собирать порт и тестовые ARM-программы (`tools/selftest.s`) |

Для запуска игры (конечный пользователь, когда хост будет готов): только Windows 10/11 x64 с видеокартой Direct3D 11 и
файлы игры; ни WSL, ни Visual Studio, ни Python не нужны. Папка с `ew2host.exe`, `ew2gl.exe` и DLL (SDL2, ANGLE)
переносима.
